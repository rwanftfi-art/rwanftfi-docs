# Technical Architecture

The RWANFTFI platform is built on a robust, modular, and secure smart contract architecture that governs all interactions, distributions, and token mechanics without central control.

## Diamond Pattern (EIP-2535) & Facets

The core of the RWANFTFI system is implemented using the Diamond Pattern (EIP-2535). This architectural choice allows the protocol to bypass the standard smart contract size limit (24KB) by splitting functionality across multiple independent modules called "Facets" (smart contract modules accessed through a single proxy contract).

The system is divided into the following key Facets:
* **AdminFacet:** Manages system parameters, roles, business sales, and the minting of special NFTs.
* **MarketingFacet:** Handles user registration, NFT purchases, and the distribution of marketing rewards.
* **FarmingFacet:** Controls the mining of NFTM and the subsequent farming cycles to generate Deflationary Assets (DA).
* **ResolverFacet:** Processes expired DA stacks, burns used Vouchers, and resolves frozen accounts.
* **PaymentFacet:** Manages user deposits, withdrawals, Voucher creation/transfers, and accumulative balance transfers.
* **TreeFacet:** Contains the logic for the 22-level binary structural marketing tree, including user placement algorithms.
* **ViewFacet:** Provides read-only functions to query user data, balances, system parameters, and tree structures.

**Upgradability Matrix:**
* **Diamond Contract (EIP-2535):** Upgradeable via Facet cuts — allows adding, replacing, or removing individual modules without redeploying the entire system.
* **TokenReserve (DA):** Upgradeable via Transparent Proxy — logic updates are possible without changing the contract address.
* **NFTs (Regular, Gift, Ambassador), GovToken, AdminContract:** Non-upgradeable — ensuring immutability of core assets and governance rules.

**Role Management:**
The system utilizes a hierarchical role structure (AccessControlEnumerable) to manage permissions securely:
* `ADMIN_ROLE`: Can grant/revoke other roles and change critical system parameters.
* `SERVICE_ROLE`: Executed by backend scripts for automated tasks (e.g., resolving expired stacks, processing cross-chain deposits).
* `SIGNER_ROLE`: Used for cryptographic signature verification to authorize specific actions like Voucher transfers.
* `MINTER_ROLE`: Authorized to mint specific tokens or NFTs.

## Balance Schema & Payment Priority

To manage the complex flow of funds, RWANFTFI employs a multi-tiered balance schema within the smart contract.

**User Balances:**
1. **Regular Balance (`balance`):** The primary wallet for available USDT. Funds here can be withdrawn at any time, used to purchase NFTs, or used to generate Vouchers.
2. **Accumulative Balance (`accumulativeBalance`):** A mandatory savings account where 20% of each marketing reward is credited immediately upon accrual.
   * **Usage:** Can only be used to purchase the same level NFT or upgrade to a higher level.
   * **Fees:** Using this balance for NFT purchases incurs a 20% fee. Transferring it to another user also incurs a 20% fee.
   * **120-Day Redistribution:** If the user does not use their Accumulative Balance within 120 days, a cascading mechanism is triggered:
     - **70% remains** with the user (the 120-day timer restarts).
     - **30%** is transferred to the user's direct upline sponsor.
     - If the upline sponsor's Income Limit is exhausted (equals zero), the 30% passes further up to the next level in the structure.
     - If no participant in the chain has an active Income Limit, the remaining funds are routed to the DA liquidity pool, increasing the DA token's value for all holders.
3. **Limit (`limit`):** Represents the maximum remaining income an NFT can generate.

**Payment Priority Order:**
When a user makes a purchase, the smart contract automatically deducts funds in a strict priority order to optimize the user's assets:
1. **Vouchers:** Consumed first if applied.
2. **Accumulative Balance:** Applied next (with a 20% fee).
3. **Regular Balance:** Finally, any remaining required amount is deducted from the available balance.

*Note: Gift Vouchers cannot be combined with the Accumulative Balance. A user must use either [Voucher + Regular Balance], [100% Accumulative], or [Accumulative + Regular Balance].*

## Security & CertiK Audit

Security is embedded across multiple levels within the platform. All logic and distribution algorithms are locked in immutable code, ensuring 100% transparency. System evolution is managed collectively via the DAO, removing centralized points of failure.

The smart contracts have passed a comprehensive independent audit by **CertiK**, a leading Web3 security firm. This audit verified the architecture, assessed vulnerabilities, and confirmed logic correctness.

The platform employs a robust multi-layer protection system for user accounts, including a three-level security system, Transaction Authentication Number (TAN) codes, a separate financial password, standard Two-Factor Authentication (2FA), and Telegram Bot verification. While users can log into the web dashboard using an email and password to view their data and balances, executing any financial transaction (withdrawal, purchase, transfer) strictly requires the connection of a Web3 cryptocurrency wallet (e.g., MetaMask, Trust Wallet).
